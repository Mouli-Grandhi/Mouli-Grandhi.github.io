KeepSake retro game console

Hackathon team project, YCP Hacks, November 2026. I did the hardware and its integration.

A game console on a Raspberry Pi where every cartridge is an NFC tag. The tag stores which game to launch and that game's save data, so your saves travel with the cartridge to any other console.

How it works

  1. The console shows "Insert cartridge" and keeps checking the NFC reader.
  2. When a tag appears, it reads a short header with the game ID, followed by that game's save data.
  3. It launches the matching game in the same window.
  4. Whenever the game's save changes, the console writes it back to the tag.
  5. Choosing "Eject cartridge" from the pause menu finishes saving and shows a "safe to remove" screen. If ejecting would lose progress, the console asks first.

Pulling the cartridge without ejecting is caught after two missed checks in a row. The game stops, and the last save on the tag is still there.

What it is useful for

  • Your save goes where you go. The save lives on the cartridge, so you can take it to any other KeepSake console and pick up exactly where you left off. There is no account to create and nothing to log in to.
  • Sharing a console is safe. Several people can play on the same console, each with their own cartridge, and nobody has to worry about someone else overwriting their save.

A classic game cartridge, like the old Nintendo ones, does this too, because the save sits on the cartridge next to the game. The catch is that every player then needs their own copy of the game. With KeepSake the games stay on the console and the cartridge carries only the save, so one console covers everyone and each player just needs a tag.

Hardware

  • Raspberry Pi 5 runs the console and the games.
  • RC522 NFC reader on the first SPI bus reads and writes the cartridges.
  • NTAG215 tags are the cartridges. Each holds 504 bytes.
  • A small 1.8 inch screen (ST7735S) on a second SPI bus shows the game that is currently playing, with its logo and name. It also shows what the console is doing: insert cartridge, loading, saving, and safe to remove, each with its own animation.
  • A gamepad or keyboard for controls.

Keeping the save on the cartridge changes what the games can do:

  • The three arcade games keep a top-10 high score table with initials on the cartridge.
  • Byte Buddy's pet keeps aging while the cartridge is out, and grows into a different adult depending on how well it was cared for.
  • Cargo Shuffle stores two custom levels, so players can swap cartridges to play each other's puzzles.
  • Crops in Pocket Farm keep growing while the cartridge is out.

The main issue: small cartridges

The biggest constraint on the whole project was the size of the NFC tags I had on hand. Each one holds 504 bytes, about as much as a few sentences of plain text. That is all the room a game gets for its save, so every game had to be designed around a very small save.

It gets tighter in practice. Each cartridge keeps two copies of the save for safety, so one copy, including its header and checksum, has to fit in half the tag: 252 bytes. The largest game, Tiny Acres, uses 250 of them.

That limit shaped the games themselves:

  • High score tables stop at ten entries, each a score and a set of initials.
  • Cargo Shuffle went from four custom levels per cartridge down to two.
  • A Pocket Farm can hold 48 objects with a backup copy, or up to 111 if it gives up the backup.
  • Nothing that can be rebuilt is stored. Maps and artwork stay on the console, and only the player's progress goes on the tag.

Fitting a save into 504 bytes

Every cartridge starts with a 15-byte header: a marker that identifies the tag as a cartridge, a format version, the game ID, the version and length of that game's save, and a write counter. The save data follows, and a CRC32 checksum closes it out.

Each game defines its own save layout and version, so one game's format can change without touching the others, and a game can convert older saves when it loads them.

The tightest squeeze was Pocket Farm. Its original save was a JSON file of about 10 KB. On the cartridge it becomes a 38-byte header plus 4 bytes for each object on the farm.

Surviving a pulled cartridge

Someone will always pull the cartridge in the middle of a save. To make that safe, each tag is split in half into two slots. A new save always goes to the slot that does not hold the newest copy, so an interrupted write can only damage the copy being written.

When a cartridge is read, both slots are checked, and the newest copy with a correct checksum wins. If one copy was damaged, the console says it recovered the backup. At worst the latest save is lost, never the whole cartridge.

A save-test mode makes this easy to try: it slows writes down to one 4-byte page every 0.1 seconds and shows the progress on screen, so you can pull the cartridge partway through and watch what loads.

How the software is put together

  • Python and pygame for the console and the games. The console owns the window and the main loop, and calls the current game every frame.
  • C for the NFC reader. The reader and tag drivers are in C, and the console calls them from Python through ctypes.
  • Background threads where the hardware is slow. Checking for a tag can take about 250 ms, so it runs off the main thread, and the status display draws at 20 frames per second in its own thread so it never slows a game down.
  • Dev mode. Without a reader attached, files stand in for cartridges, so the whole console runs on any computer.
  • One file per game. A new game is a save layout and a class with three methods: reset, update, and draw.
  • Automated tests cover the console and two of the games.

My role

I was responsible for the hardware and its integration with the rest of the console. That meant getting the NFC reader and the small screen that shows the current game connected to the Raspberry Pi and working together with the console software the team was writing.

What is left to do

It was built in a weekend, and the project's README keeps an honest list of what is not finished:

  • The status display driver and the write to the second save slot have been tested against stand-ins, and still need a full check on the real hardware.
  • Normal saves are written on the main thread, so a game can pause briefly while it saves.
  • "Power off" closes the console program but does not shut down the Pi.
